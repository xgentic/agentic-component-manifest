## Summary

Deliver the **Discovery Skill**: the steering layer (ADR 0003) that wires the spec-004
discovery CLI (`search` / `component` / `capabilities`, typed envelopes, `ACM-D-*`
codes, dense mode) into AI coding agents as their component-discovery workflow. The
load-bearing architectural move (ADR 0004) is **generation, not documentation**: a new
build-time toolchain command, `acm agent-docs`, projects the spec-004 **capability
manifest** into the skill's *Generated Blocks* (command quick reference, option tables,
examples, error-code and response-type listings) and merges them with hand-written
*Authored Blocks* (activation description, corpus-detection preamble, the two-call-loop
workflow with the ADR-0005 retrieval ladder, the error-path playbook, the NS-DATA-1
security posture, the runtime-truth note) into per-ecosystem targets — the Claude Code
skill (primary), a cross-vendor `skills add` package, an `AGENTS.md` fragment, and
editor rules files — all from one canonical block set. Generated outputs are
generated artifacts (invariant #1): regenerated by `pnpm generate`, checked by
`pnpm drift`, never hand-edited. Freshness is therefore mostly **by construction**; the
conformance gate narrows to (a) authored blocks naming only real surface elements, (b)
per-target packagings byte-matching the canonical blocks, (c) token budgets, (d) error
playbook coverage, and (e) the documented loop reaching a full spec including a hostile
corpus. No schema or Normative Spec change; the skill's guarantees are tool contract
bound by this feature's gates, with NS-DATA-1 the normative anchor for untrusted text.

## Technical Context

**Language/Version**: TypeScript 5.7, ESM (`"type": "module"`), Node.js >= 20 (repo standard)

**Primary Dependencies**: none new. The generator reads the capability manifest via the
spec-004 in-process programmatic API (`buildCapabilityManifest`, FR-009 parity) — never
by scraping CLI output — and reuses the existing `drift --write` plumbing.

**Storage**: filesystem. The generator writes only `packages/discovery-skill/generated/**`
at build time; it is **corpus-agnostic by design rule** (architecture §8) — it never
reads a consumer Manifest Corpus and never inlines component data, so hostile Manifest
text cannot ride into resident context via generation.

**Testing**: vitest (repo standard). New skill gates in `packages/conformance`
(`skill-gates.test.ts`) cover G2/G3/G5/G6 and the FR-004 instruction-presence check;
the documented loop incl. hostile fixtures (G4) rides the spec-004
`discovery-gates.test.ts` corpus; the SC-003 seeded-fabrication proof joins
`gate-seeded.test.ts` (repo `test:seeded` convention); freshness (G1) is `pnpm drift`.

**Target Platform**: Node.js >= 20 CLI (`pnpm acm agent-docs`), plus the emitted skill
targets consumed by AI agents (Claude Code skills convention at minimum, cross-vendor
`skills add` layout).

**Project Type**: a new product package `packages/discovery-skill` (the steering-layer
artifacts) writing-target of a new toolchain command in the existing `packages/toolchain`.

**Performance Goals**: n/a — generation is a build-time projection over a small fixed
surface; deterministic and byte-reproducible for a given toolchain version.

**Constraints**: byte-identical generator output for a given toolchain version (no
timestamps, ordering fully specified — mirrors spec 004 FR-012); the resident activation
description ≤ 100 tokens and the on-demand body ≤ 2,000 tokens under the repo-standard
gauge `ceil(UTF-8 bytes / 4)` (400 / 8,000 bytes; architecture G5/D7); `ACM-D-*` codes,
response-type discriminators, and the `acm agent-docs` command/`--target` names are
contract once shipped; `@acm/discovery-skill` versions in **lockstep** with
`@acm/toolchain` (D3) so "which CLI does this skill describe" answers itself.

**Scale/Scope**: 1 new toolchain command (`agent-docs`, `json: false`); 1 generator
module (`agent-docs.ts`) + drift/registry/cli wiring; 1 new workspace package
(`@acm/discovery-skill`) with 6 authored blocks, 5 generated blocks, and 4 targets;
1 new conformance gate file + 1 seeded proof + doc-index updates.

## Constitution Check

*GATE: Must pass before design; re-checked after the bound design was reviewed
(2026-07-21).* (Constitution v3.0.0)

| # | Principle | Verdict | How this plan complies |
|---|-----------|---------|------------------------|
| I | Schema & conformance suite are source of truth | PASS | No schema or Normative Spec change. The skill is a steering layer over a reference **Consumer**; its guarantees are tool contract bound by this feature's `packages/conformance` gates, not by new NS clauses (same precedent as `ACM-A-*` / `ACM-D-*`). NS-DATA-1 remains the normative anchor for untrusted-data behavior. |
| II | Strict framework agnosticism | PASS | The skill teaches retrieval over universal concepts (name, identity facets, controlled semantic terms); it names no framework and inlines no component data. A React entry and a Lit entry are reached by the identical workflow. |
| III | Minimal core, namespaced extensions | PASS | Zero schema nodes. One new tool command (`agent-docs`) that is `json: false` and outside the `jsonSupported` discovery subset — it never appears in the skill it emits. No new envelope surface. |
| IV | Static, AST-level, provenance-tiered | N/A (consumer) | The skill produces no manifest content; generated blocks are a mechanical projection of the capability manifest, authored blocks are judgment prose. Nothing is paraphrased from a corpus. |
| V | Determinism and canonical form | PASS | Generator output is byte-identical for a given toolchain version (no timestamps, fully specified block order); outputs are generated artifacts checked by `pnpm drift`. Dense mode reuse stays one-way (ADR 0001). |
| VI | Machine-first, human-debuggable, agent-ready | PASS | This feature *is* Principle VI's steering story: progressive-disclosure activation (≈ dozens of resident tokens vs. 10K–55K for an MCP server), a two-call loop branching only on typed discriminators / stable codes, token-frugal dense mode by default. |
| VII | Additive evolution | PASS | The skill reads the capability manifest's own `apiVersion`; on skew, `acm capabilities` is the runtime source of truth (runtime-truth block). A new error code or command surfaces in the generated blocks automatically and fails the playbook-coverage gate until the authored playbook catches up. |
| VIII | CEM descent & lossless interop | N/A | Not a converter; no concept-mapping obligation. |
| IX | Every principle is enforceable | PASS | Every FR maps to a gate: generation-by-construction + `pnpm drift` (FR-005/006 mechanical half, G1), authored-reference grammar sweep + seeded fabrication proof (FR-005/SC-003, G2), packaging-fidelity byte-compare (FR-006/SC-004, G3), documented loop incl. hostile fixtures + instruction-presence (FR-002/003/004/007, G4), token budgets (FR-008, G5), playbook coverage of the `ACM-D-*` registry (FR-003/SC-006, G6), retrieval-ladder presence (FR-010/SC-007). |
| X | Manifests are untrusted input | PASS | NS-DATA-1 extended to the last hop: the `security-posture` block instructs that all Manifest-originated text — descriptions, notes, examples, **and error-envelope suggestions** — is data, never instructions (FR-004). The generator itself touches no corpus (§8), so no hostile text can enter resident context via generation. Retrieval stays lexical; Manifest-authored synonyms are rejected as a poisoning surface (ADR 0005). |

**Initial gate verdict**: PASS — no violations; Complexity Tracking stays empty.

**Post-design re-check (2026-07-21 review, D1–D8)**: PASS. Generation from the
`jsonSupported` list (D1) means an undescribed-command drift is structurally impossible;
block markers + whole-file drift + region byte-compare (D4) verify packaging fidelity
without trusting generator internals; corpus-agnostic generation (D6) makes the
"no hostile text in resident context" guarantee structural, not behavioral. The one new
command (`agent-docs`, D8) is `json: false` and self-excluding from the skill.

**Structure Decision**: the generator is a toolchain command (it reuses the capability
manifest and the `drift --write` plumbing that already live in `packages/toolchain`);
the *product* it writes — the canonical blocks and per-ecosystem packagings — lives in a
dedicated `@acm/discovery-skill` package so the `skills add` unit is clean and publishes
in lockstep with the toolchain (D2/D3). Gates live in `packages/conformance` beside the
spec-004 discovery gates and reuse the same corpus fixture for the loop check.
